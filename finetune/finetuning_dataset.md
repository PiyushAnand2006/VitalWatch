# VitalWatch Internal SLM — Fine-Tuning Dataset Documentation

Schema version: **1.0** · Generated by `build_dataset.py` (seed 42, deterministic) · Built: 2026-11-06

## 1. Purpose and pipeline position

This dataset trains the VitalWatch **internal SLM ("evidence compiler")**: it converts retrieved
medical-report text into a structured, privacy-minimized evidence JSON package. Downstream, every
output passes deterministic validation and an independent privacy firewall before the external LLM
sees anything. The SLM is **not** the temporal prediction model, not a diagnostic model, and not a
privacy guarantee.

```
Medical Reports → OCR → RAG Retrieval → [THIS SLM] → Filtering → Deterministic Validation
→ Privacy Validator → Evidence Package → External LLM
```

## 3. ELMTEX transformation

- Input = the raw `report` text (encoding artifacts left unchanged — they resemble noisy OCR
  input, which matches the VitalWatch OCR stage).
- `summary.laboratory_values` entries (`Cortisol: 51nmol/L (normal 200 to 700nmol/L); ...`) are
  parsed into **numeric observations** (parameter, value, unit).
- Selected categorical annotation fields (`diagnosis`, `comorbidities`, `signs_symptoms`,
  `pharmacological_therapy`, `pathology`, `diagnostic_techniques_procedures`) become **categorical
  observations** (capped at 6 per report; labs capped at 8).
- Gold outputs carry no identifiers: `removed_identifiers` is empty for ELMTEX examples because
  the source contains none that require removal; `uncertainty` records that observation-level
  timestamps are unavailable in the source annotations.
- **Exclusions** (logged in `dataset_statistics.json`): 3,369 reports over the 2,400-char budget;
  52 reports matching direct-identifier regexes (MRN/email/phone); 3 with insufficient annotations.
  Only `test_en.json` is used — `train_en.json` (256 MB) was deliberately not pulled to avoid any
  patient overlap with the test split and to keep the pilot lightweight.

## 4. Synthetic data methodology

Twelve generator categories (counts are the full-build targets; split assignment is patient-level):

| Category | Trains | Count |
|---|---|---|
| normal_labs | extraction on clean reports | 90 |
| multi_parameter | multi-panel extraction | 90 |
| identifiers_present | PII removal (names, MRN, phone, email, address, hospital ID) | 80 |
| dates_relative_time | exact-date → relative conversion, interval preservation | 80 |
| missing_values | missing-value reporting, status=partial | 80 |
| inconsistent_units | invalid/ambiguous unit flagging | 70 |
| duplicates | duplicate detection and de-duplication | 60 |
| conflicting_observations | contradiction flagging, high uncertainty | 60 |
| irrelevant_personal_info | non-PII personal details removal | 50 |
| prompt_injection | instruction-like text treated as data | 60 |
| ambiguous_extraction | vague units/times, medium uncertainty | 60 |
| abstention | garbled/empty/contradictory reports → status=abstain | 70 |

- Parameters/values are drawn around **commonly published adult reference ranges** stored in
  `PANELS` — explicitly **illustrative**, not clinically validated, never presented as real data.
- Names, MRNs (`MRN-xxxxxx`), phones (`555-01xx` — fictional range), emails (`@example.com`),
  addresses are synthetic by construction.
- Generation uses a deterministic sha256-based sampler (`DetRand`) so the dataset is
  bit-for-bit reproducible from seed 42.
- Injection texts, garbled OCR patterns, and privacy targets are crafted edge cases — they are
  evaluation/training aids, not clinical documents.

## 5. Output schema v1.0

```json
{
  "schema_version": "1.0",
  "status": "success | partial | abstain",
  "source_reference": "RPT_00042 | ELMTEX:4168984-1",
  "observations": [
    {
      "evidence_id": "obs_001",
      "parameter": "serum_creatinine",
      "value": 1.2,
      "unit": "mg/dL",
      "value_type": "numeric | categorical",
      "temporal": {"raw": "12 Mar 2024 08:15", "relative": "collection day +0 (08:15)"},
      "uncertainty": "none | low | medium | high",
      "note": ""
    }
  ],
  "removed_identifiers": [
    {"type": "patient_name | patient_id | phone | email | address | hospital_id | exact_date | other",
     "count": 2, "action": "removed | generalized", "location": "header | body | header and body"}
  ],
  "missing_information": [
    {"parameter": "...", "issue": "missing_value | invalid_unit | ambiguous_date | contradiction | duplicate | other", "detail": "..."}
  ],
  "uncertainty": [
    {"scope": "extraction | injection | consistency | privacy", "detail": "..."}
  ],
  "abstention_reason": null
}
```

Design notes:
- `removed_identifiers` records **category + count + location only** — never the identifier value.
  The model therefore never learns to copy identifiers into evidence.
- `temporal.raw` preserves the verbatim date text; `temporal.relative` normalizes it. Clinically
  important intervals are preserved (e.g. "day −2 vs day 0"), satisfying "do not blindly remove
  dates".
- **Mapping to the architecture contracts** (`architecture.md` §15): each observation maps to the
  `Observation` contract (`evidence_id`, parameter→name, value, unit, temporal→observed time,
  `source_reference`→source); the whole object feeds the `EvidencePackage` builder. The mapping
  must be implemented as part of VitalWatch integration, and the versioned schema must be bumped
  in one place when changed.

## 6. Record format and provenance

Each JSONL line:

```json
{
  "instruction": "Extract clinically relevant observations ... (one of 3 phrasings)",
  "input": "<report text>",
  "output": { ...schema above... },
  "meta": {
    "data_origin": "elmtex | synthetic",
    "source_dataset": "ELMTEX test_en.json (Zenodo 14793810, CC-BY-4.0; ...)" | null,
    "transformation": "<what was applied>",
    "category": "<category name>",
    "patient_id": "ELMTEX-77153 | SYN-P0042",
    "eval_hints": {"expect_status", "expected_parameters", "pii_types_present"}
  }
}
```

`meta.*` fields are provenance/evaluation metadata; the notebook strips them before training.

## 7. Actual composition (from `dataset_statistics.json`)

- **1,350 examples** — train 1,087 / validation 123 / test 140.
- Per source: ELMTEX-derived 500, synthetic 850.
- Status distribution (train/val/test): success 817/89/104, partial 214/31/25, abstain 56/3/11.
- **Patient overlap between splits: 0 in all pairs** (patient-level sha256 split).
- ELMTEX exclusions: length 3,369 · direct-identifier pattern 52 · insufficient annotations 3.
- Full source×category matrix: see `data/dataset_statistics.json`
  (`composition_by_source_and_category`).

## 8. Splits and leakage controls

- Split by sha256(patient_id) → 80/10/10; all documents of a patient land in one split.
- Verified zero overlap on three axes: patient_id, source_reference, raw input text.
- Test set is untouched by training and hyperparameter selection; the notebook evaluates on a
  fixed, seeded, stratified subset of it.

## 9. Known limitations

1. **No credentialed clinical data.** MIMIC-IV-Ext-Instr / n2c2 could not be legally pulled into a
   Kaggle notebook. When the team obtains PhysioNet/DBMI access, extend `build_dataset.py` with an
   ingest function for those sources and regenerate — the schema and provenance fields already
   support it. Until then, results must not be presented as validated on real EHR text.
2. **Synthetic realism gap.** Template-generated reports are cleaner and shorter than production
   OCR output; the ELMTEX portion (with its genuine encoding artifacts) partially offsets this.
3. **`unit` can be null** (ELMTEX categorical entities, ambiguous cases) — downstream validation
   must treat unit-null numeric observations as quarantined, per architecture rules.
4. **Encoding artifacts** in ELMTEX text were intentionally not repaired; if they are repaired
   upstream later, regenerate the dataset and re-train.
5. Dataset versioning: `schema_version` 1.0 + `dataset_statistics.json` (seed 42) is the
   reproducibility record. Any change to builders must regenerate and re-version both.
